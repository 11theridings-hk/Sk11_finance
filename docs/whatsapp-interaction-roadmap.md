# WhatsApp 互動功能開發建議與可行性

面向 FINNE18／SK11：在 WhatsApp 完成公帳入數、提醒、報表等。本文說明**現況、可行性、限制與建議路線**。

相關實作：`docs/whatsapp-webhooks.md`、`src/lib/whatsapp/`、`/api/webhooks/whatsapp`。

---

## 1. 身份識別（已打通，請先填電話）

| 來源 | 說明 |
|------|------|
| **用戶資料 `contactPhone`** | 個人資料／管理後台填寫；儲存時正規化並**自動寫入 `WhatsAppBinding`** |
| **管理後台 → WhatsApp 分頁** | 手動綁定；會反寫 `contactPhone` |
| **環境變數 `WHATSAPP_USER_MAP`** | 緊急／測試用 |

來電號碼（E.164）→ 系統 User → 依權限執行指令。  
**務必填含國碼電話**（香港可填 8 位本地號，系統會補 `852`）。

## 2. 功能可行性總表

| 功能 | 可行性 | 建議型態 | 備註 |
|------|--------|----------|------|
| 查提醒（合約／事項／恆常） | ✅ 高 | 文字指令 `提醒` | **已有** |
| 公帳簡易入數 | ✅ 高 | `公帳 支 120 餐飲` → `確認` | **已有**；適合固定分類 |
| 最近紀錄／資金池／分類列表 | ✅ 高 | 文字指令 | **已有** |
| 本月收支文字摘要 | ✅ 高 | `報表`（管理員） | **已有**；非 PDF |
| 完整 PDF／會計結算包 | ⚠️ 中 | 產生後給**下載連結**或文件訊息 | ZIP／大檔不宜塞聊天；要短時簽名 URL |
| 多級分類＋附件入數 | ⚠️ 中 | 逐步對話或按鈕選單 | 文字易錯；照片需另接 media API |
| 發票／收據 OCR 上單 | ⚠️ 中 | 收圖 → OCR → 確認草稿 | 依賴現有 OCR；要下載 WhatsApp media |
| 事項／合約建立 | ✅ 中高 | 結構化指令或表單流程 | 欄位少，適合 |
| 審核通過／駁回 | ✅ 中高 | 管理員按鈕／指令 | 權限嚴格控管 |
| 薪金結算／發工資單 | ❌ 低（初期） | 僅推播「已出糧」+ 網頁連結 | 金額敏感，不建議 WhatsApp 改數 |
| 複雜報表篩選匯出 | ❌ 低 | 網頁為主 | 互動成本高於 H5 |

圖例：✅ 建議做｜⚠️ 可做但要設計｜❌ 不建議當主路徑

## 3. Meta／產品限制（設計時必顧）

1. **24 小時服務窗**  
   用戶傳訊後 24h 內可自由回覆；逾時只能用**已審核樣板訊息（Template）**（例如到期提醒）。

2. **Development vs 上線**  
   開發模式只能對測試號；正式用戶要 App／商務驗證完成。

3. **互動元件**  
   - 文字指令：最快上線（現狀）  
   - **Reply buttons / List messages**：選分類、確認入數（體驗更好）  
   - **Flows**：類似表單，適合多欄位「上單」

4. **媒體**  
   收圖／回 PDF 要用 Cloud API media endpoints；檔案要落自己的儲存再給連結較穩。

5. **安全**  
   電話≈身份，務必白名單／綁定；敏感操作要二次確認；審計備註保留 `[WhatsApp]` 前綴。

## 4. 建議分期路線

### Phase A — 身份＋查詢＋簡易入數（現在～下一迭代）

- [x] Webhook 驗證與指令骨架  
- [x] 用戶資料電話 ↔ WhatsApp 綁定同步  
- [ ] 全員填好 `contactPhone`  
- [ ] Railway 補齊 `ACCESS_TOKEN` / `PHONE_NUMBER_ID` / `APP_SECRET`  
- [ ] 到期提醒改走 Template + `WHATSAPP_REMINDER_PHONES`（或依綁定推播）

### Phase B — 更好用的「上單」

1. **List／Button**：選 收入/支出 → 常用分類 → 輸入金額 → 確認  
2. **收圖 OCR**：下載 media → 既有 OCR → 回傳草稿 → 確認入帳  
3. **管理員審核佇列**：`待審` 列表 + 一鍵通過

### Phase C — 報表與深度作業

1. `報表 本月` 文字摘要（已有）  
2. `報表 PDF`：背景產生 → 回 **短時連結**（如 `/api/exports/...` + token）  
3. 會計 ZIP **不要**直接塞 WhatsApp；改「已備妥，點連結下載」

### Phase D — 可選進階

- WhatsApp Flows 完整上單表單  
- 多語言指令  
- 會話狀態機（多步對話）存 DB，取代 `SystemSetting` pending

## 5. 「在 WhatsApp 直接上單」建議產品規格

最小可用（MVP，多數已具備）：

```text
公帳 支 88.5 交通 的士 @公司戶
→ 系統回覆摘要
→ 用戶回「確認」
→ 寫入 Record（審核戶則 PENDING）
```

下一版建議：

```text
用戶：上單
Bot：請選［支出］［收入］
用戶：支出
Bot：請選分類（List：餐飲／交通／…）
用戶：選「餐飲」
Bot：請輸入金額
用戶：120
Bot：可傳收據照片或回「略過」
→ 確認卡片 → 入帳
```

這樣比死記指令錯誤率低，也較適合非管理員同事。

## 6. 「生成報表」建議產品規格

| 等級 | WhatsApp 回覆 | 實作成本 |
|------|----------------|----------|
| L1 摘要 | 本月收入／支出／淨額／筆數 | 低（已有） |
| L2 明細精選 | 最近 N 筆或某分類合計 | 低 |
| L3 PDF | 產生後給 HTTPS 下載連結（5–15 分鐘有效） | 中 |
| L4 結算包 ZIP | 同上，僅管理員＋明確確認 | 中高 |

**不建議**把整份 PDF base64 塞進聊天；改用系統已有報表匯出邏輯 + 暫存檔／物件儲存 + 簽名 URL。

## 7. 技術注意（給後續 Agent）

- 指令與業務邏輯放 `src/lib/whatsapp/`，**不要**在 webhook route 堆業務。  
- 入數重用與網頁相同的資金池審核規則。  
- Pending 確認建議改獨立表（TTL），勿長期佔用 `SystemSetting`。  
- Template 訊息與服務窗回覆分開模組。  
- 所有 WhatsApp 寫入加來源標記，方便報表／稽核篩選。

---

## 8. 結論（給行銷／營運）

- **查提醒、簡易公帳入數、文字摘要報表**：現在就可作為 WhatsApp 主場景，可行性高。  
- **完整報表／結算包**：適合「觸發＋連結下載」，不適合全程在聊天完成。  
- **OCR 拍照上單、按鈕選單**：下階段 CP 最高的體驗升級。  
- **薪金改數、複雜篩選匯出**：維持網頁為主，WhatsApp 只做通知。

身份面：在**用戶管理／個人資料填好電話**即可；不必再維護兩套號碼。
